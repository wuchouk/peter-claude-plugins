# 引導式驗證分解問題流程

本文件定義 `/capture-test` 在 Phase 2（驗證分解）中使用的引導問題和策略。

---

## 核心原則

不問開放式的「你怎麼測」，而是用選單分解驗證需求。這樣做的好處：
1. 減少遺漏 — 選單提醒使用者可能忽略的驗證面向
2. 結構化 — 每個驗證項有明確的參數和預期值
3. 可重複 — 選單產生的定義可以直接轉成自動化

---

## 問題流程

### Q1 — 改動範圍（自動推斷 + 確認）

先從上下文推斷（TODO.md、最近對話），然後確認：

> 你剛改了 {推斷的改動}，對嗎？還是要測別的？

如果使用者說「對」→ 進入 Q2。
如果使用者補充或修正 → 更新理解後進入 Q2。

### Q2 — 驗證面向選單

根據專案的 `primitives.yaml` 動態生成選單。格式：

```
這個改動需要驗證哪些？（可多選，輸入編號）

{依 primitives.yaml 的分類列出}
```

每個選項旁邊顯示：
- primitive ID
- 一句話描述
- 需要的參數提示

### Q3 — 參數填入

對每個選中的 primitive，追問具體參數：

```
📊 sheet-column-value
  - 哪個 tab？
  - 哪欄（index 或欄名）？
  - 預期值是什麼？
  - 比對方式？（完全相等 / 包含 / regex）
```

盡量從上下文自動推斷預設值，讓使用者確認或修正。

### Q4 — 前置條件

```
測試前需要什麼準備？（可多選）

□ 清除前次測試資料
□ 準備特定測試資料
□ 設定環境變數/設定值
□ 確認服務已啟動
□ 其他（請說明）
```

### Q5 — 預期失敗模式

```
如果測試失敗，最可能原因？

建議（根據專案已知問題）：
1. {從 primitives.yaml 或 TODO.md 推斷的常見問題}
2. {另一個可能原因}

你覺得還有什麼？
```

至少收集 2 個失敗模式：一個前置條件問題，一個邏輯錯誤。

---

## 追問策略

- **使用者回答簡短時**：不追問細節，用合理預設值填入
- **使用者回答模糊時**：給出 2 個具體選項讓他選
- **使用者說「跟上次一樣」**：讀最近的 scenario file 複製驗證項目
- **使用者說「全部都要」**：全選，但只追問必要參數

---

## 批次測試的額外問題

如果使用者選了批次相關的 primitive：

```
批次測試設定：
- 跑幾筆？（預設 10）
- 要驗證每筆還是只看統計？
- 需要冪等性驗證嗎？（重跑一次看結果是否相同）
```
